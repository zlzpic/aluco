# ADR-0004: Narrow Telemetry Table Without Partitioning

**Status**: Accepted  
**Date**: 2024-07-18

## Context

The `telemetry` table stores IoT readings as narrow rows (`device_id`, `metric`, `ts`, `val`). At v1 scale (hundreds of devices, Hz rates), the team needed to decide on a storage strategy: partition by time, shard by device, use a wide format, or keep it simple.

## Decision

Use a **narrow, unpartitioned, unsharded InnoDB table** with a single composite index `(device_id, metric, ts)`.

```sql
CREATE TABLE telemetry (
    id        BIGINT AUTO_INCREMENT PRIMARY KEY,
    device_id BIGINT NOT NULL,
    ts        DATETIME(3) NOT NULL,
    metric    VARCHAR(64) NOT NULL,
    val       DOUBLE NOT NULL
);
CREATE INDEX idx_dev_metric_ts ON telemetry (device_id, metric, ts);
```

No covering index, no partitioning, no sharding.

## Consequences

### Positive
- Simplest possible schema; minimal maintenance burden.
- Flexible — any number of metrics per device, any reporting rate.
- Queries remain fast at modest scale (hundreds of devices × Hz).
- Easy to extend with additional columns (quality flags, tags) without migration complexity.

### Negative
- **Capacity ceiling is unknown** — the design deliberately avoids premature optimization.
- Table scans on large date ranges may degrade without a covering index.
- `INSERT` throughput is bounded by InnoDB buffer pool and redo log.

### Neutral
- This is the **"most reasonable day-one"** design (henceforth called the "naive baseline").
- The capacity ceiling will be measured by load testing (v2 spec §4.5) and recorded in a follow-up ADR as the factual basis for storage evolution (TimescaleDB migration, partition strategy, etc.).
- The `(device_id, metric, ts)` index covers the primary query pattern: `WHERE device_id=? AND metric=? AND ts BETWEEN ? AND ?`.

## Load Test Triggers (v2)

| Trigger | Proposed Action |
|---|---|
| `aluco.e2e.latency` p99 > 1s at 10k devices × 1Hz | Consider Kafka (ADR-0009) |
| Raw query p95 > 500ms at 100M rows | Consider TimescaleDB (ADR-0011) |
| Table volume > 2× buffer pool with degraded query latency | Consider partitioning or compression |

## Benchmark Results (2026-08-06)

> 本节为 v2 spec §4.5 压测结论回填，作为 ADR-0004 的续篇。

### 测试环境

- 机器：Windows 11, i5-12500H, 16GB RAM
- MySQL：innodb_buffer_pool_size=512M（测试设置）
- server JVM：-Xmx2g
- MQTT Broker：HiveMQ CE 2026.5

### Level 1（1,000 设备）

| 指标 | 实测值 | 门控阈值 | 结论 |
|---|---|---|---|
| sink.dropped | 0 | > 0 | ✅ 未触发 |
| e2e p99 | < 1000ms | > 1000ms | ✅ 未触发 |
| 30 分钟入库行数 | ~3,600,000 | — | 正常 |

**结论**：1k 设备为系统舒适区，无瓶颈。

### Level 2（5,000 设备）

| 指标 | 第1轮（capacity=50k） | 第2轮（capacity=200k） | 门控阈值 | 结论 |
|---|---|---|---|---|
| sink.dropped | 147,340 | 77,609 | > 0 持续增长 | ❌ **触发** |
| 丢弃率 | 72% | 38% | — | 队列持续溢出 |
| e2e p99 | ~350ms | ~350ms | > 1000ms | ✅ 未触发 |

**结论**：InMemoryTelemetrySink 在 5k 设备下无法消化 10,000 行/s 的写入速率。扩容队列容量只能缓解，不能消除瓶颈。

### 根因分析

瓶颈不在 MySQL 写入，而在 ingestion → sink 链路：
- MQTT 回调侧生产速率：~10,000 行/s
- `JdbcTemplate.batchUpdate` 消费速率：< 10,000 行/s
- 单线程消费者 + 内存队列无法吸收 burst

### Phase 2 决策

| 中间件 | 决策 | 依据 |
|---|---|---|
| **Kafka** | **引入** | sink.dropped 在 Level 2 持续增长，有明确数据依据 |
| **TimescaleDB** | **暂缓** | 未达 1 亿行，raw 查询 p95 未超 500ms |
| **Redis** | **暂缓** | Level 2 压力来自 sink 溢出次生效应，非 StateStore 自身瓶颈 |

### 遗留问题

- `@PreDestroy` flush 等待时间不足（5s），模拟器停止后队列积压数据丢失。需改为异步 flush + join。
- TimescaleDB / Redis 门控待 Kafka 引入后复测确认。
