# ADR-0002: Modular Monolith with Enforced Package Boundaries

**Status**: Accepted  
**Date**: 2024-07-18

## Context

Aluco v1 starts as a single deployable artifact (a Spring Boot JAR) but must be architected so that future services can be extracted cleanly. The team needed a package-structure convention that is enforceable at build time.

## Decision

Adopt a **modular monolith** with six logical packages and **ArchUnit** tests that encode dependency-direction rules:

```
com.aluco.server
├── alerting/      (rules, events)
├── api/           (controllers, auth)
├── device/        (device CRUD, state)
├── ingestion/     (MQTT client)
├── processing/    (telemetry processor, sink)
├── push/          (WebSocket)
└── common/        (shared DTOs, no deps on other packages)
```

Rules enforced by `ArchitectureTest`:

| Rule | Rationale |
|---|---|
| `api` may depend on all business packages; no package may depend on `api` | Controllers are entry points; business logic lives in services |
| `ingestion` and `push` must not depend on each other | They touch different transports (MQTT vs WebSocket) |
| Storage access only via `TimeSeriesStore` / `StateStore` interfaces | Enables v2 swap to TimescaleDB / Redis |
| `common` must not depend on any other package | Pure shared DTOs |

## Consequences

### Positive
- Clear mental model for future extraction (split `alerting` → service, etc.).
- Build fails fast if a developer introduces a forbidden dependency.
- Interfaces (`TelemetrySink`, `TimeSeriesStore`, `StateStore`) are explicit seams for v2.

### Negative
- Slightly higher onboarding cost; new contributors must learn the boundary rules.
- ArchUnit adds test maintenance burden.

### Neutral
- Single deployable unit for v1; no service mesh or RPC framework needed.
