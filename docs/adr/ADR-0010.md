# ADR-0010: Redis Device Shadow and ZSET-Based Offline Detection

**Status**: Accepted (pending Phase 0 benchmark data)  
**Date**: 2024-08-06

## Context

v1 stores device latest state in MySQL `device_state` table. Phase 0 benchmarks will measure `state.upsert` p99 latency and MySQL connection pool occupancy under 10k devices × 1Hz.

## Decision

Redis is introduced **only if** Phase 0 benchmarks trigger the pre-registered gate (v2 spec §4.5.4):
- `state.upsert` p99 > 20ms at 10k devices × 1Hz, OR
- Hot path (state upsert + WS push) occupies > 50% of MySQL connection pool.

**Pre-registered topology** (if triggered):
- Single Redis 7 instance
- Key `aluco:state:{deviceKey}` → HASH: `metrics`(JSON), `lastSeenAt`(epoch ms), `online`(0/1)
- Key `aluco:last_seen` → ZSET: member=deviceKey, score=lastSeenAt
- Upsert via Lua script (HSET + ZADD in one atomic operation)
- **Offline detection via ZSET range query** (NOT Redis keyspace notifications; see Alternatives)

## Consequences

### Positive (if triggered)
- Sub-millisecond state upsert latency, independent of MySQL connection pool.
- Natural TTL support: ZSET range query for stale devices is O(log N + M).
- Offline detection is deterministic and recoverable (ZSET is persisted to AOF/RDB).

### Negative
- **Additional infrastructure**: Redis to deploy, monitor, backup.
- **Eviction policy risk**: `maxmemory-policy allkeys-lru` could evict state; must set explicit `maxmemory` and monitor `used_memory`.
- **Keyspace notifications explicitly rejected**: see Alternatives.

### Neutral
- If benchmarks do NOT trigger the gate, Redis is deferred.
- The `StateStore` interface is the seam; implementation swap requires no business logic changes.
- `OfflineDetection` interface decouples sweep logic from storage.

## Alternatives Rejected: Redis Keyspace Notifications

Keyspace notifications (`notify-keyspace-events`) were evaluated and **rejected** for offline detection:

| Issue | Impact |
|---|---|
| **Event loss on restart** | Pending notifications are lost when Redis restarts; offline events missed. |
| **Fire-and-forget delivery** | No guarantee client receives all events; requires polling fallback anyway. |
| **Debugging difficulty** | Event ordering and deduplication hard to verify in production. |
| **ZSET alternative is simpler** | `ZRANGEBYSCORE aluco:last_seen 0 (now-60s)` is deterministic, testable, and recoverable. |

## Benchmark Gate (Pre-Registered)

| Condition | Trigger Action |
|---|---|
| `state.upsert` p99 > 20ms at 10k devices | Switch to Redis |
| MySQL connection > 50% occupied by hot path | Switch to Redis |
