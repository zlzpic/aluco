# ADR-0005: Stable Telemetry Envelope as Cross-Version Contract

**Status**: Accepted  
**Date**: 2024-07-18

## Context

Devices publish telemetry as JSON messages. The server must parse this envelope reliably. Future versions (v2 Go gateway, mobile SDKs) will need to produce or consume the same format. A contract change requires coordinated releases across all producers, which is expensive.

## Decision

Define the **telemetry envelope** (`v=1`, `deviceId`, `ts`, `seq`, `metrics`) as a **stable cross-version contract**. The `v` field is an integer; v1 is fixed at `1`. Future versions increment `v` (e.g., `2`) but must remain backward-compatible (accept `v=1` for a deprecation period).

```json
{
  "v": 1,
  "deviceId": "TH-0001",
  "ts": 1752739200000,
  "seq": 42,
  "metrics": { "temp": 35.2, "humidity": 61.0 }
}
```

Parsing and validation live in `common.EnvelopeCodec` — a pure class with no Spring dependencies — so it can be reimplemented in Go, Rust, or any language without pulling in the server runtime.

## Consequences

### Positive
- `EnvelopeCodec` is the single source of truth for envelope semantics.
- Go gateway (v2 §7) and future SDKs reimplement the same contract independently.
- Drop reasons (`PAYLOAD_TOO_LARGE`, `UNSUPPORTED_VERSION`, `DEVICE_TOPIC_MISMATCH`, etc.) are machine-readable and countable for observability.

### Negative
- Adding new top-level envelope fields requires a version bump and coordinated producer rollout.
- The `seq` field is currently only recorded (not validated for gaps); promoting it to a reliability signal requires a new envelope version.

### Neutral
- The command envelope (`DeviceCommand`) is a separate schema and is **not** versioned by `v`.
- Device-side envelope generation (simulator) should match `EnvelopeCodec` drop rules to avoid preventable message loss.
