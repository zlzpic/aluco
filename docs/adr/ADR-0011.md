# ADR-0011: Migrating Telemetry to TimescaleDB

**Status**: Accepted (pending Phase 0 benchmark data)  
**Date**: 2024-08-06

## Context

v1 stores telemetry in a narrow MySQL table (`telemetry`) with a single composite index `(device_id, metric, ts)`. Phase 0 benchmarks will measure raw query p95 latency and table volume growth under 100M rows.

## Decision

TimescaleDB is introduced **only if** Phase 0 benchmarks trigger the pre-registered gate (v2 spec §4.5.4):
- Raw query p95 > 500ms for single-device 1-hour range at 100M rows, OR
- Table volume > 2× `innodb_buffer_pool_size` with query latency degrading proportionally.

**Pre-registered migration topology** (if triggered):
- PostgreSQL 16 + TimescaleDB 2.17 extension
- Hypertable `telemetry` with 7-day chunks
- Continuous aggregates `telemetry_1m` and `telemetry_1h` (AVG(val), refresh every 1m/10m)
- Native compression enabled at 7 days (target: ≥10× compression ratio)
- Query routing: `interval=raw` → hypertable; `1m/5m` → `telemetry_1m`; `1h/1d` → `telemetry_1h`

## Consequences

### Positive (if triggered)
- **Time-series optimized**: hypertables partition by time automatically; no manual partitioning needed.
- **Compression**: 7-day native compression targets ≥10× size reduction; retained data compresses further.
- **Continuous aggregates**: pre-computed rollups make 1h/1d queries orders of magnitude faster.
- **Retention policies**: configurable (currently disabled by default; see spec §6.3).

### Negative
- **New database**: PostgreSQL to deploy, monitor, and backup alongside MySQL.
- **Dual-write period**: during migration, data exists in both MySQL and TimescaleDB; consistency must be verified.
- **Cross-database FK impossible**: `telemetry` in TimescaleDB cannot FK to `device` in MySQL; resolved via `device_tombstone` dual-lookup pattern.
- **Rollback cost**: cutting over back to MySQL requires accepting a data gap; documented in README.

### Neutral
- The `TimeSeriesStore` interface is the seam; implementation swap requires no business logic changes.
- Backfill tool (`aluco-sim backfill`) supports `--target mysql|timescale` for migration.
- If benchmarks do NOT trigger the gate, TimescaleDB is deferred to v3 or until explicit re-evaluation.

## Alternatives Rejected

| Alternative | Reason Rejected |
|---|---|
| **MySQL partitioning** | Manual range partitioning on `ts` is viable but requires DBA skill to manage; TimescaleDB automates this. |
| **ClickHouse** | Superior compression but higher operational complexity; overkill for v2 scale. |
| **Keep MySQL indefinitely** | Acceptable until benchmarks show degradation; ADR documents the decision point. |

## Benchmark Gate (Pre-Registered)

| Condition | Trigger Action |
|---|---|
| Raw query p95 > 500ms at 100M rows | Migrate to TimescaleDB |
| Table volume > 2× buffer pool with degraded queries | Migrate to TimescaleDB |
