# ADR-0006: Command ACK as a Standalone Schema

**Status**: Accepted  
**Date**: 2024-08-06

## Context

Devices need to acknowledge downlink commands (e.g., SET_INTERVAL). The team considered two approaches: (1) upgrade the telemetry envelope to v=2 and add an ack field, or (2) define a separate schema for command acknowledgments.

## Decision

Command ACK uses a **standalone schema** (`CmdackMessage`), not an envelope upgrade. The envelope `v` field stays at 1; the ACK is a distinct MQTT topic (`aluco/{siteId}/{deviceKey}/cmdack`) with its own validation rules.

## Consequences

### Positive
- **Separation of concerns**: telemetry envelope versioning is independent of command ACK evolution.
- **Simpler device firmware**: devices only need to parse one envelope format for telemetry and one lightweight ACK format.
- **No breaking change to existing v=1 producers**: the envelope contract is frozen.

### Negative
- Two message formats to maintain and test.
- Future ACK schema changes require a separate version field (currently `v=1` in `CmdackMessage`).

### Neutral
- The `v` field in the ACK schema serves the same purpose (version negotiation) but is not tied to the envelope version.
- The ACK topic pattern mirrors the cmd topic: `aluco/{siteId}/{deviceKey}/cmdack`.

## Alternatives Considered

- **Envelope v=2 with ack field**: rejected because it couples ACK evolution to telemetry envelope evolution, which would force coordinated firmware updates for all producers.
- **Embed ACK in cmd response**: rejected because MQTT QoS 1 pub/sub is the natural transport for ACKs; no request-response correlation needed.
