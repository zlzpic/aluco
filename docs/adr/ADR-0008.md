# ADR-0008: Documented Orphan Semantics for Historical Data

**Status**: Accepted  
**Date**: 2024-08-06

## Context

When a device is deleted, its historical telemetry (`telemetry` table) and alert events (`alert_event` table) retain the `device_id` foreign key. The team needed to decide whether to: (1) cascade-delete historical data, (2) keep it as orphans, or (3) implement soft-delete.

## Decision

**Orphan semantics with explicit tombstone table** (v2 spec §4.4.1):
- `telemetry` and `alert_event` rows are **not deleted** when a device is deleted.
- `device_tombstone` table records `(device_id, device_key, deleted_at)` for deleted devices.
- `device_key` is resolved via `device ∪ device_tombstone` union (not just `device`).
- `alert_event` gains a `device_key` snapshot column (backfilled at V2 migration) for display without joining `device`.
- **Soft-delete is explicitly rejected** (see Alternatives).

## Consequences

### Positive
- **Historical data is preserved**: telemetry and alert history remain queryable after device deletion.
- **No FK violation**: orphaned `telemetry` rows still resolve to a `device_id` via `device_tombstone`.
- **No application logic change required for historical queries**: `MySqlTimeSeriesStore.deviceId()` now checks both `device` and `device_tombstone`.
- **Alert display never breaks**: `alert_event.device_key` snapshot column decouples alert listing from the `device` table.

### Negative
- **Storage growth**: deleted devices' data persists until manual cleanup.
- **No automatic cleanup policy**: an operator must periodically purge tombstoned data if retention is a concern.
- **Additional table and query complexity**: two lookups instead of one for device_id resolution.

### Neutral
- The tombstone table is small (one row per deleted device) and acts as an index into historical data.
- Future cleanup jobs (e.g., "purge telemetry older than 90 days for tombstoned devices") can be added without schema changes.

## Alternatives Rejected

| Alternative | Reason Rejected |
|---|---|
| **Cascade delete** telemetry/alert_event | Destroys audit trail; violates "preserve history" requirement |
| **Soft-delete** (add `deleted_at` to device) | Would require every query to filter `deleted_at IS NULL`; rejected after design review |
| **ON DELETE SET NULL** on FKs | `device_id` is NOT NULL in `telemetry`; changing to nullable adds complexity |
